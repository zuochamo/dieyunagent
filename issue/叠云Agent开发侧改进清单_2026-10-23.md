## 二、P0 · 直接导致返工或明显降低效率

### AGT-01　SSH 远程工作区无符号索引与 LSP，代码定位基本不可用

- **现象**：在远程工作区无法按函数名定位代码，只能整文件读取或 grep 兜底。
- **证据**：
  - `read_symbol` 共 59 次，其中 58 次作用于远程工作区，**失败 46 次（79%）**；错误码 `SYMBOL_NOT_FOUND` 44 次、`FS_READ_FAILED` 2 次。本地唯一 1 次成功。
  - `lsp` 远程调用 2 次，**100% 失败**（`LSP_QUERY_FAILED`）。
  - 日志根因：`[lsp][diagnostics] project scan ssh://.../dieyundaizhang tsc+eslint+ruff+prettier files=0 errors=0` —— 扫描到的文件数为 0。
- **影响**：定位一个函数需整文件读取，token 与轮次翻倍；长会话很快触发上下文压缩，进一步打断思路。
- **建议**：
  1. 远程索引改为服务化，或在远端提供 grep 级降级的符号检索（明确标注 `degraded: true`）；
  2. 扫描到 0 文件时**抛出错误**，不要静默返回 `errors=0`。

### AGT-02　`fs_edit` 字面量匹配过于脆弱

- **现象**：编辑中文长文本时频繁因原文不匹配而失败，需重读重试。
- **证据**：调用 231 次，失败 19 次（8.2%）。其中 `MISSING_OLD` 10 次、`FS_EDIT_NOT_FOUND` 3 次、`FS_EDIT_NOT_UNIQUE` 2 次、`FS_EDIT_NO_CHANGE` 2 次；远程 164 次中失败 13 次。
- **影响**：模型需精确复述长段原文，缩进或全角符号稍有偏差即失败。
- **建议**：
  1. 支持「行号区间 + 模糊匹配（忽略空白与全半角差异）」；
  2. 失败时返回**最接近片段 + diff**，而非仅一个错误码；
  3. `FS_EDIT_NOT_UNIQUE` 时列出所有候选位置，便于一次性消歧。

### AGT-03　`host_exec` 的 shell 语义与环境处理存在问题

- **现象**：使用量最大的工具（54%）也是踩坑最集中的地方，多数问题在远程与 Windows 场景。
- **证据**：失败 43 次（`EXCEPTION` 34、`BLOCKED` 6、`CHAIN_LIMIT` 3）。已确认的典型坑：
  - 远程执行 `set PGPASSWORD=… && psql` 会**卡住 60~90 秒**，须改写为 `PGPASSWORD=… psql -w` 前缀形式；
  - Windows 侧为 cmd，分号会截断命令，`python -c` 多语句报错；
  - 中文输出默认 GBK，反复出现 `UnicodeEncodeError: 'gbk'`，需手工 `set PYTHONIOENCODING=utf-8`；
  - `del /q` 一类清理命令被 `BLOCKED` 拦截，且未说明命中了哪条规则。
- **建议**：
  1. 显式声明 shell 类型与目标平台；
  2. 支持独立的 `env` 参数；
  3. 默认 UTF-8 输出；
  4. 长任务（>60s）自动转后台并返回 handle；
  5. `BLOCKED` 需回传命中的具体规则与放行方式。

### AGT-04　`fs_list_dir` 对本地目录返回 0 项（功能性 Bug）

- **现象**：本地目录真实有文件，工具返回空数组，导致误判「产物未生成」。
- **证据**：10-20 对 `C:\Users\DIEYUN3\Desktop\觅柔` 返回 0 项；最终改用 `host_exec dir` 才核对到实际文件。
- **影响**：会引发重复生成、重复写入，浪费大量时间。
- **建议**：修复列表实现（编码 / 路径转义）；无法读取时**明确报错**，不要返回空数组。

## 三、P1 · 稳定性与可诊断性

### AGT-05　远程与 MCP 连接断开会静默发生

- **证据**：
  - `MCP(mcp-daizhang) 会话已断开，下次调用将重新拉起`（10-21 15:23）
  - `MCP(mcp-pixel)` 同上（10-23 14:42）
  - `SSH leased reconnect gateway: SSH 未连接，正在恢复…`（10-23 18:50）
  - 断开时 `stderr 尾部为空`，**看不到断开原因**。
- **建议**：保留最后一次 stderr 与退出码；UI 显示「连接已断开 / 正在重连」状态，避免让工具调用先超时再暴露。

### AGT-06　错误码粒度过粗，无法指导处置

- **证据**：`web_fetch` 16 次失败全为 `TOOL_ERROR`；`host_exec` 34 次全为 `EXCEPTION`；另有 6 次失败 `errorCode` 为空。
- **影响**：无法区分反爬、网络、鉴权、参数错误，Agent 只能盲目换引擎重试。
- **建议**：细分错误码（HTTP 状态、是否被反爬、是否需浏览器接管），并附 `suggestedFix`。

### AGT-07　联网抓取失败率偏高

- **证据**：`web_fetch` 66 次失败 16 次（**24.2%**）；`web_search` 27 次失败 7 次（**25.9%**）。已核实 `api.github.com` 未鉴权返回 401、`hub.docker.com` 抓取直接 `fetch failed`。
- **建议**：失败时自动降级到内置浏览器重试一次，并回传「该站点需登录 / 需 JS 渲染」的结论，减少无效重试。

### AGT-08　长会话前端卡顿

- **证据**：`main.log` 记录 8 次 `freeze snapshot`，`silentMs` 2.3s ~ **10.0s**，单次 longtask 560~700ms，`domNodes` 6.6k~7.9k，`messages` 16~36 条；集中在 10-21 13:07 与 **10-23 14:24~14:40 同一会话连续 7 次**。
- **建议**：消息列表虚拟滚动、代码块懒渲染、重计算移出主线程。

### AGT-09　`agent_clarify` 会长时间挂起且可能异常

- **证据**：调用 6 次，**p50 等待 300 秒**，其中 3 次 `EXCEPTION`。用户不在场时整轮空等 5 分钟。
- **建议**：支持可配置超时，超时后按默认方案继续执行，并在回复中明确「已按 A 方案执行」。

### AGT-10　上下文压缩与模型切换导致跨天任务上下文断裂

- **证据**：单会话 `compaction_round_count` 已达 15~17，库中 3 份压缩归档；用户消息长度 p50 仅 **75 字**，上下文几乎完全依赖 Agent 侧维持；期间混用 4 个模型（deepseek-v4.1-flash 1952 次、glm-5.3-flash 1104 次、deepseek-flash 552 次、deepseek-v4-flash 398 次）。
- **影响**：压缩或换会话后需重读材料，输出风格也会漂移。
- **建议**：会话内锁定模型并在切换时提示；压缩摘要保留「文件路径 / 表名 / 命令 / 结论」等结构化锚点并保证可检索。

## 六、口径与偏差说明

1. 上述 166 次失败中，`fs_edit MISSING_OLD`、`read_symbol SYMBOL_NOT_FOUND` 有一部分源于 Agent 侧工具用法不当（如一次性替换过大段落），并非纯产品缺陷。建议开发侧按「基础设施缺陷（AGT-01、AGT-04、AGT-05、AGT-06）」与「Agent 用法规范」分开排期。
2. 遥测只覆盖工具层，**模型侧编排失误（重复读取、无效重试）没有量化数据**；AGT-03、AGT-10 属日志观察推断，非统计结论，已在正文标明证据来源。
3. 全部数字可由 `tool-telemetry.jsonl` 与 `diecloud-memory.sqlite` 复算，便于开发侧独立校验。
