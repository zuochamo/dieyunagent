## 1. 现象（原始对话摘录）

用户：

> 你导入了？我看到有高沧路农机加油站 这个账套。 你可以导入试试吗？

Agent 回复原文（截至中断处，以下为完整显示内容）：

```
## 进展汇报

**已完成的部分：**
1. ✅ 高沧账套在系统里确认存在（customerCode=189，状态 pending，
```

—— 到此结束。按原计划后续还应有第 2、3 项（卡点、待用户决策）与结论段，全部缺失。界面无「生成中断 / 出错」提示，消息以正常完成态渲染。

用户随后追问：

> 怎么汇报内容这么少？这是叠云agent的bug吗？

## 2. 判定

- **不是没生成**：中断点停在列表第 1 项括号内部，末尾为逗号（`状态 pending，`），属生成中途被切断，非主动精简。
- **不是数据/业务问题**：同一问题在追问后重新作答，内容完整、层级正常，篇幅远大于被截断那条。
- **性质**：内容已产生但未完整送达，用户侧看到「回复莫名很短」且无任何告警 —— 属静默降级。

## 3. 影响

1. 用户误判为 Agent 能力不足（本次已实际发生），直接损害可信度；
2. 丢失的段落恰是结论与下一步动作（「我并未执行导入」「请你二选一」），导致业务动作中断；
3. 无报错，事后无法从界面区分「截断」与「本来如此」，只能靠人工回忆定位。

## 4. 可能原因假设（分层列出，均待开发侧验证）

| 层 | 假设 | 验证方法 |
|---|---|---|
| A 模型输出 | 单条回复触发 `max_tokens` 上限被硬截断 | 查该轮请求的 max_tokens 与 usage.completion_tokens 是否触顶 |
| B 流式传输 | SSE/WebSocket 流在末包前断开，`finish_reason` 缺失却未判为异常 | 查该轮流日志、finish_reason 是否为空 / 有无 stop 事件 |
| C 上下文压缩 | 长会话触发 compaction，与在建消息生成并发导致掐断 | 查该 run 是否触发压缩、压缩事件时间戳是否与生成本轮重叠 |
| D 持久化 | 落库时按字段长度截断 | 比对库中该条消息长度 vs 界面显示长度 |
| E 前端渲染 | Markdown 在未闭合列表/代码块处提前终止渲染 | 取库中原文换渲染器对照 |

**建议排查顺序**：先做 D/E 二分（取库中原文长度与原文尾部，和界面显示对比）。若库中原文完整 → 前端渲染或传输层；若库中即截断 → 生成端或持久化层。

- 终端日志：`.../高沧/.dieyun/terminals/integrated.log`（内含客户端系统版本与本机 cwd）

## 6. 复现建议

1. 让 Agent 输出一条包含 3 段以上列表 + 表格 + 结论段的长回复（此类汇报通常 800~1500 字）；
2. 在长会话、上下文接近压缩阈值时重复；
3. 观察特征：内容中途停止 / 末尾是逗号或未闭合代码块 / 无任何 error 提示 / finish_reason 为空。

## 7. 期望修复与验收标准

1. **不静默截断**：任何非正常结束（finish_reason ≠ stop、流中断、落库截断）都在消息尾部显式标注「回复被中断」，并保留已生成内容；
2. **支持续写**：提供「继续生成」，可从断点续写，用户不必重问；
3. **可观测**：截断事件上报 runId、结束原因、token 用量、耗时，便于统计发生率；
4. **渲染兜底**：前端对未闭合 Markdown 结构做标示，避免把不完整内容渲染成「看起来完整」的短回复。
